A move from another panel is an installation, an import of the users and a switch of the old domain. Each step has its own page; this one is about their order and what goes between them.

## Where to install

- **On a new server.** The old panel keeps working until you have checked everything, and clients notice nothing until the domain is switched.
- **On the old panel's server.** The installer does not stop on busy ports: the protocols on them get other free ports, see [Installation](/mikan/en/start/install/#what-the-installer-asks). The mikan panel runs in the server's own network, so the import reaches the old panel at its usual address. If it serves plain http on its port, `http://127.0.0.1:PORT` works (for 3x-ui, with its secret path): plain `http://` is allowed only to this server and the local network. If it serves https itself (Marzban with `UVICORN_SSL_*`, 3x-ui with a certificate), give the address you open it at in the browser, `https://domain:port`. The steps go a little differently on the same server, see [below](#on-the-same-server).

The old panel's node servers become mikan nodes like any other: the command with a key from the **Nodes** page, see [Nodes](/mikan/en/nodes/nodes/).

## The order

<Steps>

1. [Install mikan](/mikan/en/start/install/) and go through the [first steps](/mikan/en/start/first-steps/).

2. Connect the nodes and set up the [plan](/mikan/en/billing/plans/) the users will come to: the import does not start without a plan, and the users get its protocols, traffic reset and server groups.

3. [Move the users](/mikan/en/operations/import/#move-users): "Check", then "Import".

4. Set up the [old subscription links](/mikan/en/operations/import/#old-subscription-links): the path, for Marzban and PasarGuard also the signing secret, and the subscription port if the old panel gave subscriptions on another port.

5. Point the domain the old panel gave subscriptions on at the mikan server. mikan needs a certificate for that name: make the domain the panel's domain (**Settings → General → Server**, see [Change the domain or address](/mikan/en/start/domain/#change-the-domain-or-address)) or the [subscription domain](/mikan/en/subscriptions/domain/). Until there is a certificate, apps may complain about the name.

6. Try a couple of old links: the user's card shows their old link (Remnawave, 3x-ui) or that it works. Links revoked in the old panel open again in mikan: reissue them.

7. Once the old links open in mikan, the old panel can be turned off.

</Steps>

### On the same server

While the old panel runs, it holds its subscription port, and mikan will not take it ("Port … is taken by another program on the server"). Port 80, needed for the old domain's certificate, is often held by its nginx or Caddy. So steps 4, 5 and 7 go like this:

<Steps>

1. Move the users and set the old links' path and, for Marzban and PasarGuard, the signing secret.

2. Stop the old panel, or at least what serves its subscriptions and holds port 80 (its web server). From this moment subscriptions do not open until step 4 is done.

3. Set the subscription port and the old links' domain, and wait for the certificate. If nginx or Caddy stay on port 80, see [Your own certbot or nginx on port 80](/mikan/en/start/domain/#your-own-certbot-or-nginx-on-port-80).

4. Try a couple of old links.

</Steps>

:::caution[An import is a snapshot]
The import moves users as they were when it started. What changes in the old panel after it (renewals, traffic used, new users) does not come over by itself. Running the import again takes only new names: those already in mikan are skipped. So switch the domain soon after the import.
:::

## Moving mikan to another server

On the old server, as root:

```sh
mikan move root@NEW_IP
```

The command does what the steps below describe: a backup, an install of mikan on the new server with the same panel port, a copy of the backup (its sha256 checked) and the restore. Then it opens in the new server's ufw the panel port and the ports the old one let in for mikan: the subscription port, the ports of the protocols and of the cascade, whatever the panel and the node listen on. The installer itself opens 80, 443 and the spare ports.

- **SSH.** The system's `ssh` with your keys and ssh-agent: no password is asked for or kept. Check first that `ssh root@NEW_IP` logs in without a password and that the host key is accepted. A user other than root works too if it has `sudo` without a password. Another SSH port: `-p 2222`.
- **The new server must be empty.** If mikan is already installed there, the command stops. `--force` replaces its data with this panel's, a copy of the old ones stays in its `/opt/mikan/backups`. A node of another panel does not do, even with `--force`.
- **The version.** The new server gets the latest stable release, and a backup goes only onto the same version or a newer one. If the old server runs a newer (test) version, the command stops at the check, before installing anything: update the new server to that version first, then run `mikan move --force`. A build that is not a release (`dev`) is moved only with `--force`.
- **The old panel keeps running** until you stop it. What changes in it after the backup does not reach the new server, so switch the domain right away. At the end of the move `--stop-old` stops it with its payment adapters and turns off its daily update, so that the update does not start the panel again. To bring it back: `systemctl enable --now mikan-update.timer` and `mikan restart`; to remove it: `mikan uninstall` (the data stay in `/opt/mikan`).
- `--dry-run` prints the steps and does nothing.

After the command, steps 4 and 5 below are left: the domain or the server address, and the nodes. The command prints them. If a step fails, it stops and prints what is left to do by hand, from that step on.

### Step by step by hand

A mikan backup goes onto a freshly installed server, see [Restore](/mikan/en/operations/backups/#restore).

<Steps>

1. On the old server: `mikan backup`, then copy the archive from `/opt/mikan/backups` to the new server. `mikan url` shows the panel port.

2. On the new server, install mikan with the same panel port: `--port PORT`, see [the flags](/mikan/en/start/install/#unattended-for-scripts). The panel port is in `/opt/mikan/config.json` (`PANEL_PORT`) and in the database, both come back with the backup, while the installer opens in ufw only the port it set up itself. A port you opened by hand on the old server (for example a subscription port outside the spare ones) has to be opened again: `ufw allow PORT/tcp`. `mikan doctor` shows a closed panel port and closed protocol ports; it does not check the subscription port.

3. Restore the backup: `mikan restore /path/to/mikan-….tar.gz`.

4. If the server has another IP, change "Server address" in **Settings → General → Server**, and point the domain's A record at the new server. Subscription links are built from this address, see [Change the domain or address](/mikan/en/start/domain/#change-the-domain-or-address). With a [subscription domain](/mikan/en/subscriptions/domain/), clients' links do not change in a move.

5. The connection to the nodes comes back by itself. If "Node API from the panel's IP only" is on for them, the rule lifts itself after 15 minutes and comes back with the new address, see [Hardening a node](/mikan/en/nodes/hardening/#node-api-from-the-panels-ip-only).

</Steps>

Your own site in `/opt/mikan/data/panel/www` is not in the backup, move it separately.
