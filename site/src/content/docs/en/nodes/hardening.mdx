:::note[New in 0.5.2.0]
The node's API from the panel's IP only and the redirect are new in 0.5.2.0 and exist for remote nodes.
:::

Two settings in **Nodes → the node → Configure** make a node's server less visible to scanners. The node on the panel's own server ("Own node") has neither: it talks to the panel over a socket and opens no API port. The third, [open ports of the server](#open-ports-of-the-server), exists on every node: it decides what the node's clients reach on the server itself.

## Node API from the panel's IP only

The **Node API from the panel's IP only** switch. On a node added since 0.5.2.1 it is on from the start; on one added earlier it stays as it was. The node's API port is needed only by the panel, but scanners find any open port. The pinned certificate and the key keep them out, yet they still reach the TLS handshake. With this setting the node answers on the API port to the panel's addresses only.

It works in two layers:

1. The node itself refuses connections from other addresses.
2. The node asks its server to put in an `nftables` firewall rule (a table `inet mikan_api`) that drops TCP to the API port from every address but the panel and loopback. A scanner does not reach the node at all. The rule touches nothing else of the firewall, and ufw's rules still apply to what it lets through. The rule is kept by the `mikan-apilock` system service on the node's server.

The node takes the panel's address and the address the panel connected from by itself. If the panel reaches nodes from an IP other than its public one (NAT, a second address), add the addresses in the **More panel addresses** field: addresses or networks separated by commas, up to 16.

:::tip[If the panel moved to another IP]
The node is not lost. If the panel has not shown up on the node for 15 minutes, the rule lifts itself, the panel connects from its new address, and the rule comes back with it.
:::

### If the rule gets in the way: mikan api-lockdown

On the node's server as root:

```bash
mikan api-lockdown status   # the rule's state (the command with no argument does the same)
mikan api-lockdown off      # lift the rule at once
```

`off` removes the rule and opens the port, and the node stops refusing within ten seconds. The rule comes back the next time the panel connects to the node with the setting on. To keep it from coming back, turn the switch off in the node's settings in the panel. The command works only on a node's server: on the panel's server it stops with an error.

`mikan doctor` on the node shows the rule's state too and suggests the command.

### No nftables

Without the `nftables` package the node still closes the port itself (the first layer), but scanners reach it. The node card then shows "The node closes the port itself, but its server's firewall has no rule" and the reason. Install the package on the node's server:

```bash
apt install nftables
```

The rule appears by itself within a minute.

A node server set up before 0.5.2.0 gets the system service for the rule after `mikan update` on it, see [Nodes](/mikan/en/nodes/nodes/#updating-nodes-from-the-panel).

## HTTP → HTTPS on port 80

The **HTTP → HTTPS** switch. The node takes port 80 and answers plain HTTP with a 301 to https, as a real site does. A closed port 80 gives away a bare VPN server, and the redirect makes it look like an ordinary site.

HTTP-01 certificates keep being issued: the node handles the certificate authority's checks on `/.well-known/acme-challenge/` as before, see [Node certificate](/mikan/en/nodes/nodes/#node-certificate).

Do not turn it on if another web server on this server needs port 80. If the port is taken, the node card shows "Port 80 cannot be taken" and the reason.

## Open ports of the server

:::note[New in 0.5.2.1]
Exists on every node, the panel's own node included.
:::

The **Open ports of the server** field. A connection from a node to its server's own address goes through the `lo` interface, which a firewall usually lets through whole. So a client connected to the node could reach whatever listens on the server's public address, even a port closed from outside: a database, a monitoring service, SSH open to your own IP only.

The node's core does not let those connections through. On the server's own address clients reach only:

- ports 80 and 443: a site or a reverse proxy on the server is there for anyone anyway, and without these it would open from everywhere but this node;
- on the panel's own node also the panel's port and the subscription port: otherwise a client going through it could not open the panel or refresh the subscription.

A panel on another server is not affected: to the node that is someone else's address.

If clients need a service on the node's server, such as your own DNS, put its port in this field: separated by commas, up to 16 ports. The port opens for both TCP and UDP. The firewall does not stop these connections, so leave SSH and databases out.

The core learns the server's addresses from its network interfaces. On a server behind NAT the public address is not on an interface, and this protection does not refuse those connections: they go out into the hoster's network and come back from outside, like any other.

A node older than 0.5.2.1, or a node under a panel older than 0.5.2.1, does not turn this protection on.

## How the server looks from outside

:::note[New in 0.5.2.1]
The line "How the server looks from outside" is in the check of every node.
:::

**Nodes → Check node** ends with what in the node's setup makes its server stand out to someone who looks at it from outside: a scanner that connects to its ports, a network that sees where its clients go. These are warnings, not errors: everything works, but the server is easier to tell from an ordinary site.

| Warning | What to do |
|---|---|
| Several camouflage sites on the node | Keep one site for all the REALITY protocols: an ordinary server does not hold the certificates of several other sites |
| A camouflage site that is a mail name or dynamic DNS | Take an ordinary site: "Find near the server" lists those first |
| A protocol on the default `www.microsoft.com` | Pick a site next to the server: Microsoft's certificate on a hoster's address stands out |
| TLS protocols on three or more ports of their own | Turn on the [shared port 443](/mikan/en/nodes/shared-443/): one port is left to see, as a site has |
| A server behind a CDN takes direct connections too | Keep the protocols behind a CDN on a node of their own: direct connections give away the address the CDN hides |
| The node's API port is open to anyone | Turn on "Node API from the panel's IP only", see above |
| A domain has "vpn", "proxy" or a protocol's name in it | Take a neutral name: it is seen in every connection and stands in the certificate |

The check reads the panel's settings alone and does not connect to the node for it, so the line is there for a node that does not answer too.

What the panel cannot check, but is worth keeping in mind: a CDN knows the address of the server it hides from its own settings; one subscription, a trial one too, names the addresses of all the servers in it.
