The **Diagnostics** page in the panel's menu gathers what you used to need SSH for. Pick a server: the panel's server or any node.

## Logs

The last 2000 lines of the panel's log and of each node's. Tokens, keys, passwords, subscription links and secret paths are cut out before a line reaches the log. There is a level filter (all, warnings, errors), a text search, a refresh every 5 seconds and copying of the lines shown.

## Check

**Run the check** runs `mikan doctor` on the server itself, not in a container: Docker and the containers, ports, ufw rules, port 80, the clock, DNS, access to GitHub and GHCR, disk and memory. Every line has a hint on what to do. Waiting for the report takes up to a minute.

**Restart** restarts the containers of the panel's server or of a node. The panel or the node is unreachable for a couple of seconds.

How it works: the panel writes a request file into its data directory and a systemd unit on the server runs the command and returns the result. For a node the request goes over the node API. A server installed before 0.5.2.0 needs one `mikan update` for this; until then the check answers "the server did not answer".

## Reachability

Checks whether the server opens for users in Russia. Handy before you buy a server or install mikan on it: type an IP or a domain and up to three TCP ports. Port 22 is open on almost any server with SSH, start with it.

The [Globalping](https://globalping.io) service does the check: its points in home and mobile internet in Russia (where the blocks are) and in Russian data centres connect to the ports three times each. To compare, points in Germany, the Netherlands and Finland do the same. The result in one line:

- **opens from Russia**: it opens from everywhere;
- **does not open for everyone**: some operators block it;
- **blocked in Russia**: it opens from Europe, not from Russia. Another IP or another host is needed;
- **answers from nowhere**: the port is closed, the host's firewall drops it, or the server is off.

"1 of 3 got through" is a sign of a block too: an open port lets every try through.

:::caution[What this check does not see]
The server's address goes to Globalping. The check sees a block of the IP and the port, not a block by protocol and not the whitelists of mobile operators. Without a key Globalping gives about 250 checks an hour from one address; the result is kept for 2 minutes, and one check runs at a time.
:::

## Geo bases

:::note[New in 0.5.2.0]
The geo base check is new in 0.5.2.0.
:::

Sites and apps tell a client's country by geo bases, and the bases often disagree. If one base puts your server's IP in another country, a service shows the wrong region or refuses. The **Geo bases** tab shows what the bases think of an address.

Enter the server's IP or domain (the hint offers your nodes' addresses) and press "Check the geo bases". The panel asks ten public bases (MaxMind, ipinfo.io, IP2Location and others), which takes up to ten seconds. The result in one line: "All N bases put the address in: country" or "The bases disagree: country by N of M". Below, each base with its answer, the ones that disagree are marked. A base that did not answer is marked too: did not answer in time, a request limit or no answer. The result of a recent check is shown from the cache.

:::caution[What this check does not see]
The server's address goes to public geo bases. How services such as YouTube or Netflix see the IP is not shown: they have bases of their own.
:::

For nodes the same check is in the "Check node" window, see [Nodes](/mikan/en/nodes/nodes/#country-in-the-geo-bases).

## A node takes a lot of memory

The VPN core usually takes tens of megabytes. Its memory grows with open connections and UDP sessions, so first find out whether there are many. On the node's server:

```bash
curl -s --unix-socket /var/lib/docker/volumes/mikan_run/_data/node.sock http://node/v1/health | grep -oE '"(conns|proc_rss|mem_used|mem_total)":[0-9]+'
```

`proc_rss` and `mem_used` are in bytes here, and `conns` is the users' open connections and UDP sessions. If the memory is high and `conns` is low, take the profiles while the memory is high and attach them to your report:

```bash
curl -s --unix-socket /var/lib/docker/volumes/mikan_run/_data/node.sock http://node/debug/pprof/heap -o heap.pb.gz
curl -s --unix-socket /var/lib/docker/volumes/mikan_run/_data/node.sock 'http://node/debug/pprof/goroutine?debug=1' -o goroutines.txt
```

The profiles hold no keys and no client addresses: only the program's functions and how much memory and how many goroutines fall to each.

From 256 MiB on, the node writes a `node memory` line to its log: the memory taken, the heap, the stacks, the goroutines and the connections. A new line comes when the memory has grown by another quarter. Near 60% of the server's memory the node collects garbage more often, to leave room for the panel and its database. This is a soft limit: traffic that really needs the memory still gets it, at the cost of more CPU.

## Terminal

The tab appears for an operator with "Terminal" level access and only for the servers you ticked for it. Details and limits are in [Support access](/mikan/en/operations/support-access/#terminal).

## When the panel does not open

Then the page is out of reach. Run `mikan doctor` on the server: the same report in the terminal. For a support ticket there is `mikan support <code>`, see [The mikan command](/mikan/en/operations/cli/).
