**Settings → Import** moves users from Marzban, PasarGuard, Remnawave or 3x-ui. You do not need access to the old panel's database: everything goes through its API, and the old panel itself is not changed. The whole move in order, from installing to turning the old panel off: [Moving to mikan](/mikan/en/start/migrate/).

## Move users

<Steps>

1. Pick the panel and enter the **Address of the old panel**, for example `https://panel.example.com`, without the admin path. For 3x-ui the address goes with the port and the panel's secret path, as you open it in the browser: `https://panel.example.com:2053/path`.

2. Access:
   - **Marzban**: the administrator's username and password;
   - **PasarGuard**: a username and password, or an API key with the `users:read` permission;
   - **Remnawave**: an API token with permission to read users;
   - **3x-ui**: the administrator's username and password, or an API token (Settings → API tokens, in newer versions). If the administrator signs in with a two-factor code, a token is needed. In 3x-ui 3.11 the username and password are random at install (3x-ui's log shows them on the first start), `admin`/`admin` does not work. The import does not take a self-signed certificate: if the panel has no real certificate, give an `http://` address, which works only to this server or within the local network.

3. Pick a **Plan**: users get its protocols, traffic reset rule and server groups.

4. "Check" shows how many users were found, how many are new and how many are already here.

5. "Import" starts the import in the background, so you can close the page.

</Steps>

The traffic limit, used traffic, term, device limit and note are carried over. Users whose names already exist in mikan are skipped. The old reset rule, groups and connections are not carried over. Users "on hold" start their term at the moment of import.

### 3x-ui

In 3x-ui clients live inside the inbounds, so the import gathers them into users this way:

- clients with the same `subId`, on any inbounds, are one user, one subscription. The user is named after the `email` of the first of them (in the order of the inbounds), the note is their comments, the contact their Telegram ID;
- 3x-ui has limits per client, and the user gets their sum: the traffic limit is the sum of the limits, used traffic the sum of what they used; if one of the clients has no limit, the user has none. The term is the latest one, and a client without a term makes the user's term endless;
- the device limit is `limitHwid` of 3x-ui 3.x, and in the versions without it the limit of addresses at once (`limitIp`), the largest of the clients';
- a term "from the first use" (a negative `expiryTime`) starts at the import, as "on hold" does from the other panels;
- a client without a `subId` comes over as a user of its own, without an old link;
- a client that is only on inbounds of protocols mikan has not (VMess, WireGuard, MTProto and others) does not come over: "Check" lists it among those mikan will not take, with the reason. If the same `subId` has clients on mikan's protocols, the user comes over with them, and such a client's limits, term and traffic are not added in. mikan's protocols are VLESS, Trojan, Shadowsocks, Hysteria2 and TUIC.

A user is disabled only if every client of its `subId` is. A client 3x-ui turned off by itself when its term or traffic ran out comes over expired or over its limit, not disabled, so it works again after a renewal. The limits and terms of the inbounds themselves are not carried over.

:::caution
Links that were revoked in the old panel work again after the import. If that matters, reissue them.
:::

## Old subscription links

For clients to change nothing, point the old domain at the mikan server and set up the **Old subscription links** card:

- **Path of the old links**: `sub` for Marzban and PasarGuard, `api/sub` for Remnawave. For 3x-ui it is the "Subscription path" of its Settings → Subscription (`sub` by default): the old link is the client's `subId`, which comes over as it is. Empty: off.
- Marzban and PasarGuard also need the **Signing secret of the old panel**. It is stored in the old panel's database:

  ```sql
  SELECT secret_key FROM jwt;
  ```

  Without it, the old links will not open.
- Set the subscription port in **Settings → Subscription** if the old panel served subscriptions on a different port.

The bot accepts old links, and the user card shows the old link (Remnawave, 3x-ui) or that it works. Reissuing a link disables the old one too.

## The Bedolaga sales bot

If you sold Remnawave subscriptions through the [Bedolaga](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot) bot, its accounts can come over after the users: who owns which subscription, the balances and the transaction history.

<Steps>

1. Bring over the users of this bot's Remnawave first, as above.

2. Turn on the bot's Web API: `WEB_API_ENABLED=true` and a key in `WEB_API_DEFAULT_TOKEN` in its `.env`, then restart the bot. By default the API listens on `127.0.0.1:8080` on the bot's server. If mikan runs on another server, open the port to it only, or put an HTTPS proxy in front of the API.

3. In **Settings → Import** pick **Bedolaga** and enter the API's address (`http://127.0.0.1:8080` when the bot is on this server) and the key.

4. **Check** shows how many accounts found their subscriptions, how much money on the balances comes over and how many transactions.

5. **Bring the accounts over** runs it in the background.

</Steps>

What comes over:

- **The subscription's owner.** An account finds its subscription by its link: the link holds the Remnawave short UUID, which the import kept as an old link. Without a link, the account is looked up by the contact `tg:<id>` that the Remnawave import writes. A subscription that already has an owner in mikan keeps it. After the move the client does not have to link the subscription in mikan's bot again.
- **The balance.** The rubles in the bot go to mikan's internal balance, once: a second run does not add them again. If mikan's balance is kept in another currency (**Payments → Payment methods**), the amount is converted at its rate. The client sees it in the balance history marked "Bedolaga".
- **The transaction history.** Completed top-ups, payments and refunds are kept apart from mikan's payments: they are not counted as revenue and cannot be refunded from the panel. `GET /api/v1/balances/{tg_id}` gives them in `imported`.

These accounts no longer get "new clients only" promo codes: mikan counts them as clients from the day the bot first saw them. Referrals, promo groups and autopay do not come over.
